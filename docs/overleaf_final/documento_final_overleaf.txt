\section{Objetivo General}

Diseñar y desarrollar una base de datos relacional transaccional (MySQL), que centralice, controle y valide las operaciones de la aerolínea ecuatoriana Pegaso. El sistema resuelve problemas críticos de la industria aeronáutica:

\begin{itemize}[leftmargin=1.5cm]
    \item[\textcolor{pegaso-gold}{$\blacktriangleright$}] \textbf{Concurrencia:} Múltiples agentes emitiendo boletos simultáneamente sobre el mismo vuelo sin generar sobreventa no controlada, mediante bloqueos a nivel de fila (\texttt{SELECT ... FOR UPDATE}).
    \item[\textcolor{pegaso-gold}{$\blacktriangleright$}] \textbf{Integridad Referencial:} 22 tablas normalizadas con restricciones \texttt{FOREIGN KEY}, \texttt{CHECK}, \texttt{UNIQUE} y \texttt{ENUM} que imposibilitan la inserción de datos inconsistentes.
    \item[\textcolor{pegaso-gold}{$\blacktriangleright$}] \textbf{Auditoría y Regulación:} Triggers que registran automáticamente cada operación y prohíben la eliminación física de registros de pasajeros, cumpliendo con regulaciones de seguridad aeroportuaria.
    \item[\textcolor{pegaso-gold}{$\blacktriangleright$}] 
\end{itemize}

\subsection{Restricciones y Constraints Destacados}

\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{PRIMARY KEYS (PK):} Definidas explícitamente en las 22 tablas del modelo para garantizar la identidad única de cada registro.
    
    \item \textbf{FOREIGN KEYS (FK) - 28 relaciones:} Destaca el uso estandarizado de \textbf{ON UPDATE CASCADE} en todas las llaves para la propagación de cambios, así como estrictos controles de eliminación:
    \begin{itemize}
        \item \textbf{ON DELETE RESTRICT} en la mayoría de dependencias críticas (personas, vuelos, aeropuertos, aviones, etc.) para mantener el historial intacto y soportar el modelo de soft-delete.
        \item \textbf{ON DELETE CASCADE} en dependencias directas que deben destruirse si desaparece el padre (\texttt{tripulacion\_vuelo}, \texttt{boletos}, \texttt{asientos\_vuelo}, \texttt{pases\_abordar}).
        \item \textbf{ON DELETE SET NULL} excepcionalmente en \texttt{asientos\_vuelo(boleto\_id)} para liberar el asiento si se cancela un boleto específico.
    \end{itemize}

    \item \textbf{UNIQUE Compuestos (8 restricciones):}
    \begin{itemize}
        \item \texttt{boletos(vuelo\_id, numero\_asiento)}: Impide que dos pasajeros tengan el mismo asiento.
        \item \texttt{puertas\_embarque(aeropuerto\_iata, numero)}: Evita duplicar el número de puerta en un mismo aeropuerto.
        \item \texttt{modelos\_avion(fabricante, modelo)} y \texttt{configuracion\_asientos(modelo\_id, fila, columna)}.
        \item \texttt{rutas(origen\_iata, destino\_iata, hora\_salida)}: Previene rutas idénticas a la misma hora exacta.
        \item \texttt{personas(tipo\_documento, numero\_documento, nacionalidad)}: Garantiza identidad única por documento.
        \item \texttt{tripulacion\_vuelo(vuelo\_id, empleado\_id)}: Evita la doble asignación del mismo tripulante.
        \item \texttt{asientos\_vuelo(vuelo\_id, configuracion\_asiento\_id)}: Bloquea la duplicidad de la configuración espacial dentro de un mismo vuelo.
    \end{itemize}

    \item \textbf{UNIQUE Simples (13 restricciones):} Implementadas para garantizar identificadores de negocio irrepetibles en campos críticos como \texttt{codigo\_vuelo}, \texttt{nombre} (para roles, clases de servicio y tarifas), \texttt{codigo\_empleado}, \texttt{numero\_licencia}, \texttt{username}, \texttt{codigo\_pnr}, \texttt{numero\_boleto}, \texttt{numero\_tag} de equipaje, y \texttt{codigo\_barras}.

    \item \textbf{CHECK Constraints (7 restricciones):}
    \begin{itemize}
        \item En \texttt{vuelos}: \texttt{fecha\_hora\_llegada > fecha\_hora\_salida}.
        \item En \texttt{boletos}: \texttt{precio >= 0}.
        \item En \texttt{equipajes}: \texttt{peso\_kg > 0}.
        \item En \texttt{modelos\_avion}: \texttt{capacidad\_pasajeros > 0}.
        \item En \texttt{rutas}: \texttt{distancia\_km > 0} y \texttt{duracion\_estimada\_min > 0}.
        \item En \texttt{empleados}: \texttt{salario >= 0}.
    \end{itemize}

    \item \textbf{Valores por Defecto (DEFAULT):} Implementados en la estructura para optimizar la inserción de datos y definir estados iniciales lógicos, cumpliendo con el diseño físico:
    \begin{itemize}
        \item \textbf{Fechas automáticas:} Uso de \texttt{DEFAULT CURRENT\_TIMESTAMP} en tablas de auditoría, reservaciones y emisión de pases de abordar.
        \item \textbf{Estados operativos iniciales:} \texttt{estado ENUM(...) DEFAULT 'PROGRAMADO'} (vuelos), \texttt{DEFAULT 'DISPONIBLE'} (asientos y puertas), y \texttt{DEFAULT 'PENDIENTE'} (reservaciones).
        \item \textbf{Banderas lógicas:} \texttt{esta\_activo BOOLEAN DEFAULT TRUE} aplicado en personas, empleados y usuarios para el correcto manejo de la política de soft-delete.
    \end{itemize}
\end{itemize}

\section{Implementación Funcional (Frontend)}

El frontend fue desarrollado con \textbf{Python (Flask)} + \textbf{HTML5/CSS3/JavaScript puro}, siguiendo una arquitectura MVC con herencia de templates Jinja2. El diseño visual utiliza una paleta corporativa azul marino (\texttt{\#0F2B46}) y dorado (\texttt{\#C9A84C}), inspirada en aerolíneas latinoamericanas.

\begin{notabox}[Stack Tecnológico]
\begin{tabularx}{\linewidth}{@{}l X@{}}
\textbf{Backend:} & Python 3.11 + Flask + Jinja2 \\
\textbf{Frontend:} & HTML5, CSS3 (1{,}449 líneas), JavaScript ES6 (164 líneas) \\
\textbf{Conexión BD:} & mysql-connector-python con pool de 5 conexiones \\
\textbf{Autenticación:} & Sessions + werkzeug.security (SHA-256 / bcrypt) \\
\textbf{Templates:} & 21 archivos HTML en 5 directorios \\
\end{tabularx}
\end{notabox}

\subsubsection{Cálculo Dinámico de Precios}

El precio de cada boleto se calcula en el backend  mediante la siguiente fórmula:

\[
\text{Precio} = \underbrace{(30 + d \times 0.15)}_{\text{Precio base por distancia}} \times \underbrace{f_c}_{\text{Factor clase}} \times \underbrace{f_t}_{\text{Factor tarifa}}
\]

Donde $d$ es la distancia en kilómetros de la ruta, $f_c$ es el factor de la clase de servicio (Economy = 1.00, Premium = 1.50, Business = 2.50, First = 4.00) y $f_t$ varía según la familia tarifaria (Light = 1.0, Standard = 1.2, Full = 1.4, Flex = 1.6).

\begin{exito}[Ejemplo real del sistema]
\textbf{UIO $\rightarrow$ GYE} (280 km): \$72.00 base $\times$ 1.00 (Economy) $\times$ 1.2 (Standard) = \textbf{\$86.40} \\
\textbf{UIO $\rightarrow$ MIA} (2{,}880 km): \$462.00 base $\times$ 2.50 (Business) $\times$ 1.4 (Full) = \textbf{\$1{,}617.00}
\end{exito}

\section{Procedimientos Almacenados}

Se implementaron \textbf{7 procedimientos almacenados} para soportar las operaciones críticas del sistema. Cumpliendo estrictamente con las exigencias del proyecto, todos estos procedimientos integran: \textbf{parámetros} de entrada (\texttt{IN}) y salida (\texttt{OUT}), \textbf{control transaccional} completo (\texttt{START TRANSACTION} / \texttt{COMMIT} / \texttt{ROLLBACK}), \textbf{control de errores} (\texttt{DECLARE EXIT HANDLER FOR SQLEXCEPTION}) y \textbf{control de bloqueos} por fila (\texttt{SELECT ... FOR UPDATE}) para garantizar la consistencia ante peticiones concurrentes.

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{l X c c}
\toprule
\textbf{Procedimiento} & \textbf{Propósito} & \textbf{FOR UPDATE} & \textbf{Params OUT} \\
\midrule
\texttt{sp\_crear\_reservacion} & Genera PNR único de 6 chars, valida email & No & PNR, resultado \\
\texttt{sp\_emitir\_boleto} & Emite e-ticket de 13 dígitos, valida capacidad + sobreventa & \textbf{Sí} & boleto, resultado \\
\texttt{sp\_checkin\_pasajero} & Check-in con asiento, valida clase, genera boarding pass & \textbf{Sí} & código barras, resultado \\
\texttt{sp\_registrar\_equipaje} & Tag IATA, valida franquicia de tarifa y peso $\leq$ 32kg & No & tag, resultado \\
\texttt{sp\_cancelar\_reservacion} & Soft-delete: cancela reserva + boletos + libera asientos & \textbf{Sí} & resultado \\
\texttt{sp\_cambiar\_estado\_vuelo} & Transición de estados, cancela boletos si vuelo cancelado & No & resultado \\

\subsubsection{Ejemplo: \texttt{sp\_emitir\_boleto} (Control de Sobreventa)}

\begin{lstlisting}
-- Bloqueo exclusivo sobre el registro del vuelo
SELECT estado, limite_sobreventa INTO v_estado_vuelo, v_limite_sobreventa
FROM vuelos WHERE id = p_vuelo_id FOR UPDATE;

-- Conteo de boletos activos
SELECT COUNT(*) INTO v_vendidos 
FROM boletos WHERE vuelo_id = p_vuelo_id AND estado NOT IN ('CANCELADO');

-- Validacion de capacidad + politica de sobreventa
IF (v_vendidos >= (v_capacidad + v_limite_sobreventa)) THEN
    SET p_resultado = 'ERROR: Capacidad maxima excedida.';
    ROLLBACK;
END IF;
\end{lstlisting}

\subsubsection{Ejemplo: \texttt{sp\_checkin\_pasajero} (Validación de Clase)}

\begin{lstlisting}
-- Obtener clase del boleto
SELECT REPLACE(UPPER(cs.nombre), ' ', '_')
INTO v_clase_boleto
FROM boletos b 
JOIN clases_servicio cs ON b.clase_servicio_id = cs.id
WHERE b.id = p_boleto_id FOR UPDATE;

-- Obtener clase del asiento seleccionado
SELECT c.clase_servicio INTO v_clase_asiento
FROM asientos_vuelo av
JOIN configuracion_asientos c ON av.configuracion_asiento_id = c.id
WHERE av.id = p_asiento_vuelo_id FOR UPDATE;

-- Validacion cruzada: la clase debe coincidir
IF v_clase_boleto != v_clase_asiento THEN
    SET p_resultado = 'ERROR: El asiento no corresponde a su clase.';
    ROLLBACK;
END IF;
\end{lstlisting}

\subsubsection{Ejemplo: Protección contra eliminación física}

\begin{lstlisting}
CREATE TRIGGER trg_proteger_eliminacion_persona
BEFORE DELETE ON personas
FOR EACH ROW
BEGIN
    SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'No se permite la eliminacion fisica 
    de personas. Use desactivacion (esta_activo = FALSE)';
END;
\end{lstlisting}

Esta restricción es crítica en la industria aeronáutica: las autoridades de aviación civil pueden requerir el historial completo de un pasajero años después de su viaje. El sistema utiliza \textbf{eliminación lógica} (campo \texttt{esta\_activo = FALSE}) en lugar de \texttt{DELETE}.

\subsubsection{Ejemplo: Vista de Ocupación de Vuelos}

\begin{lstlisting}
CREATE OR REPLACE VIEW vw_ocupacion_vuelos AS
SELECT 
    v.id AS vuelo_id,
    r.codigo_vuelo AS numero_vuelo,
    m.capacidad_pasajeros AS capacidad_total,
    COUNT(b.id) AS boletos_vendidos,
    SUM(CASE WHEN b.estado IN ('CHECKIN','ABORDADO','COMPLETADO') 
        THEN 1 ELSE 0 END) AS pasajeros_chequeados,
    ROUND((COUNT(b.id) / m.capacidad_pasajeros) * 100, 2) 
        AS porcentaje_ocupacion,
    SUM(b.precio) AS ingresos_totales
FROM vuelos v
JOIN rutas r ON v.ruta_id = r.id
JOIN aviones a ON v.avion_matricula = a.matricula
JOIN modelos_avion m ON a.modelo_id = m.id
LEFT JOIN boletos b ON v.id = b.vuelo_id 
    AND b.estado NOT IN ('CANCELADO', 'NO_SHOW')
GROUP BY v.id, r.codigo_vuelo, m.capacidad_pasajeros;
\end{lstlisting}

\section{Conclusiones}

El proyecto Pegaso Airlines demuestra la aplicación de los conceptos de Sistemas de Bases de Datos en un dominio de alta criticidad operativa. Los principales logros técnicos incluyen:

\begin{enumerate}[leftmargin=1.5cm]
    \item \textbf{Integridad transaccional:} Los 7 procedimientos almacenados garantizan que ninguna operación quede en estado inconsistente, incluso ante fallos o concurrencia.
    
    \item \textbf{Seguridad multinivel:} Desde el frontend (roles, sesiones) hasta el backend (triggers, constraints), cada capa del sistema valida de manera independiente las reglas de negocio.
    
    \item \textbf{Realismo aeronáutico:} El sistema refleja fielmente las operaciones de una aerolínea comercial: códigos PNR estándar, tags IATA de equipaje, límites regulatorios de peso (32 kg), control de sobreventa, clases diferenciadas y auditoría completa.
    
    \item \textbf{Arquitectura escalable:} La separación entre Ruta (entidad maestra) y Vuelo (instancia) permite escalar a múltiples frecuencias diarias sin redundancia de datos.
\end{enumerate}
